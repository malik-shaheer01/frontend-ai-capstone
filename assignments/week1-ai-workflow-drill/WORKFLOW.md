# WORKFLOW.md — Vague vs. Precise Prompting Drill

I built the same thing twice: an account settings form with a name field, an email field, and a notifications checkbox. Round 1 came from a single lazy sentence — "Build me a settings form" — with the output accepted exactly as it came out, no edits. Round 2 came from a fresh session with a real spec: file references, explicit constraints, example behavior, and a verification step before calling it done. Two branches, `round-1-vague` and `round-2-precise`, so neither run could contaminate the other.

The gap shows up immediately in correctness. Round 1's submit handler never calls `e.preventDefault()`, so clicking Save just reloads the page and throws away whatever was typed — the kind of bug that's invisible until someone actually tries to use the form. It also doesn't validate anything: type garbage into the email field and it still fires `alert('Saved!')`. Round 2 checks `preventDefault()` first, then runs validation before anything is treated as saved, and I confirmed the three cases from the spec actually work in a browser — empty submit, bad email, valid submit — not just that the code looked right on paper.

Accessibility tells the same story. Round 1's "labels" are just text sitting next to the inputs, with no `for`/`id` link to them — a screen reader has no idea they're related. Nobody asked for that connection, so it didn't happen. Round 2 has proper `<label for>` pairing, `aria-invalid` and `aria-describedby` on bad fields, and a live region that announces how many fields need attention. None of it is exotic — it's just what "write it properly" turns into once you actually say what "properly" means.

Round 2 also has tests and Round 1 doesn't, which meant Round 2's validation logic (`validation.js`) got checked against nine cases — empty name, empty email, missing `@`, missing domain, spaces, valid input — before I ever touched the DOM.

Here's the part I didn't expect going in: Round 2 also had a bug, and it was mine. I wrote `validation.js` with `module.exports` and `app.js` with an ES `import`, which is a straight mismatch — the two don't talk to each other. The unit tests didn't catch it, because the test file used the same module system as `validation.js`, so it passed clean while the actual page was broken. I only found it by loading the page in a browser and clicking Save — nothing happened, no error printed anywhere obvious, just a form that quietly did nothing. Fixing it meant adding `"type": "module"` to `package.json` and making everything consistent, then rerunning the tests and the click-through to be sure.

That's really the whole lesson. Round 1 took about two minutes and felt fast. Round 2 took longer and felt slower while I was writing the prompt and the tests. But Round 1's speed was fake — the reload bug and the missing validation were still sitting there, just not found yet. Round 2's bug got caught in the same sitting, before the branch ever left my machine. "Fast" and "already broken" turned out to be the same thing.
